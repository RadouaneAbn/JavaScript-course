01

Foundations

Types, scope, coercion, operators, control flow, strings and numbers. The rules everything else sits on.

1.1Values and types

JavaScript has seven primitive types (string, number, bigint, boolean, undefined, null, symbol) and one object type. Functions, arrays, dates, maps and regexes are all objects. Primitives are immutable and compared by value; objects are compared by reference.

Coming from C++

There is no int, float or char. Every number is an IEEE-754 double, which gives exact integers up to 2^53 - 1. Bitwise operators silently convert to 32-bit signed integers. For real 64-bit integers use BigInt.

Explain the behaviour

typeof returns the primitive type name for the seven primitives, but every non-primitive reports 'object' — except functions, which are a special case returning 'function', and null, which returns 'object' because of a historical bug. That is why typeof cannot tell an array, a date or a map apart from a plain object.

Explain the behaviour

typeof null is 'object' — a bug from 1995 that cannot be fixed for compatibility. NaN is a number by type and is the only value that is not equal to itself, which is why Number.isNaN and Object.is exist. Finally, 0 and -0 are distinct numbers: === treats them as equal, but Object.is (and 1/x) can tell them apart.

Explain the behaviour

Assigning a primitive copies its value, so changing the copy never affects the original. Assigning an object copies only the reference, so two names can point at one object and mutating through one is visible through the other. Strings are immutable primitives: toUpperCase() returns a brand-new string and leaves the original untouched.

1.2var, let, const and scope

Use const by default and let when you must reassign. Avoid var: it is function-scoped, hoisted and initialised to undefined, which hides bugs. let and const are block-scoped and live in the temporal dead zone (TDZ) from the start of the block until their declaration runs.

Explain the behaviour

var declarations are hoisted to the top of their function and initialised to undefined, so reading one before its line prints undefined instead of throwing. let is hoisted too, but stays uninitialised from the start of the block until its declaration line — that gap is the temporal dead zone, and reading during it throws a ReferenceError.

Explain the behaviour

var is function-scoped, so a for loop shares one i; by the time the arrows run, i is already 3, so all three return 3. let is block-scoped and creates a fresh binding on every iteration, so each arrow captures its own j and returns 0, 1, 2.

Explain the behaviour

const freezes the binding, not the value. You can freely mutate the object a const points to, but you cannot make the name point at a different object — that throws a TypeError.

Explain the behaviour

A function declaration hoists as a complete, callable function, so you can call add before its line. A function expression assigned to a var hoists only the variable name as undefined, so calling it first throws a TypeError.

Coming from C++

const here is like T* const, not const T*: the binding is fixed, the thing it points to is not. Use Object.freeze for (shallow) immutability.

1.3Equality and coercion

=== compares without conversion. == runs the abstract equality algorithm, which converts types in surprising ways. Use === everywhere except the one idiom x == null, which is true for both null and undefined.

Explain the behaviour

=== compares type and value with no conversion, so 1 and '1' differ. == first coerces both sides to a common type, which produces surprises like 0 == false and [] == false. The one useful idiom is x == null, true for both null and undefined.

Explain the behaviour

Only eight values are falsy: false, 0, -0, 0n, '', null, undefined and NaN. Everything else is truthy — including '0', 'false', empty arrays and empty objects, and even new Boolean(false).

Explain the behaviour

+ prefers strings: if either operand is a string it concatenates, otherwise it adds. That is why 1 + 2 + '3' is '33' but '1' + 2 + 3 is '123'. Every other arithmetic operator converts to numbers first, so '5' - 2 is 3 and the unary + turns things into numbers.

Tip

+ concatenates if either side becomes a string; every other arithmetic operator converts to numbers. Convert explicitly with Number(x), String(x) and Boolean(x) and the surprises disappear.

1.4Operators you may be underusing

Explain the behaviour

?? returns the right side only when the left is null or undefined, whereas || falls back on any falsy value — so 0 ?? 3 is 0 but 0 || 3 is 3. Optional chaining ?. short-circuits to undefined the moment anything in the path is nullish, instead of throwing.

Explain the behaviour

||= assigns only when the current value is falsy, &&= only when it is truthy, and ??= only when it is null or undefined. They are the assignment versions of ||, && and ??.

Explain the behaviour

** is exponentiation (and (-2) ** 3 needs the parentheses — a negative base is otherwise a syntax error). Bitwise operators convert to 32-bit signed integers, and ~~x / x | 0 are the classic fast way to truncate toward zero. The comma operator evaluates everything and returns the last value, and void 0 is the canonical way to get undefined.

Explain the behaviour

Packing many on/off options into one integer uses one bit each. | sets a flag, & tests it, &~ clears it, and << builds the individual bit masks. It is compact and fast, and worth it when you have many flags or need dense storage.

1.5Control flow

Explain the behaviour

for...of walks the values of any iterable (arrays, strings, maps, sets), while for...in walks the enumerable string keys of an object, including inherited ones — which is why arr.extra shows up but array elements do not. Use .entries() to get index and value together.

Explain the behaviour

A labelled statement lets break and continue target a specific outer loop, not just the innermost one. switch(true) evaluates cases as real boolean expressions, giving a clean way to pick the first matching range instead of a chain of if/else.

Explain the behaviour

JavaScript lets you replace many if/switch statements with expressions: a ternary picks a value, && returns the right side only when the left is truthy, and an object lookup replaces a switch. These keep the result directly assignable and composable. The do...while loop runs its body at least once before testing the condition.

1.6Strings and template literals

Explain the behaviour

Strings are immutable, so every method returns a new string. trim, padStart/padEnd, split/join, at (which supports negative indexes), slice, includes, repeat and localeCompare cover most day-to-day needs.

Explain the behaviour

Backticks allow ${...} interpolation of any expression and real multi-line strings. String.raw returns the raw text with backslashes untouched, so String.raw`C:\new\table` keeps the backslashes instead of interpreting \n and \t.

Explain the behaviour

length counts UTF-16 code units, so an emoji counts as 2 while spreading it ([...str]) counts code points (1). A combined character like é can be one code point or two, fixed with normalize(). Intl.Segmenter counts grapheme clusters — what a human sees as one character.

Strings are immutable sequences of UTF-16 code units. .length, indexing and slice work on code units; spreading a string ([...str]) or using for...of walks code points; Intl.Segmenter walks grapheme clusters, which is what a human calls a character.

1.7Numbers and BigInt

Explain the behaviour

Doubles cannot represent 0.1 or 0.2 exactly, so their sum is 0.30000000000000004, not 0.3. Compare with a tolerance (Math.abs(a - b) < Number.EPSILON) or use integers. Integers are exact only up to 2^53 - 1; past that use BigInt, which is exact at any size.

Explain the behaviour

parseInt/parseFloat parse a leading number and ignore trailing junk, while Number requires a clean numeric string (Number('42px') is NaN but Number('') is 0). ['10','10','10'].map(parseInt) returns [10, NaN, NaN] because map passes the index as the radix.

Explain the behaviour

Math.round rounds half up toward +∞, so -2.5 rounds to -2, unlike trunc/floor/ceil which behave differently for negatives. Number.isInteger and Number.isSafeInteger check the value without coercing, unlike the global isFinite. Helpers like clamp are trivial with Math.min/Math.max.

Explain the behaviour

BigInt is exact at any size, but it cannot be mixed with number in arithmetic — that throws. Division truncates toward zero (7n / 2n is 3n). Comparisons work across the two types, but 2n == 2 is true while 2n === 2 is false, because == coerces but === does not.

02

Functions

The heart of the language: closures, this, higher-order patterns, recursion.

2.1Declarations, expressions and arrows

Explain the behaviour

A declaration, a function expression and an arrow all define functions, but they differ in hoisting, this and arguments. The arrow form is terse, returns an object literal only when wrapped in parentheses, and — like a named expression — reports a .name. .length counts declared parameters.

Explain the behaviour

Functions are first-class objects: they can be stored in objects, passed as arguments, returned from other functions, and even carry their own properties. A function that returns another function (like makeGreeter) is a closure factory — the inner function remembers greeting.

Explain the behaviour

Normal functions get their own this (chosen by the call), an arguments object, can be used as constructors, and — as declarations — hoist fully. Arrow functions have none of these: this and arguments come from the surrounding scope, calling them with new throws, and as const/let expressions they sit in the temporal dead zone. That is why arrows suit short callbacks, while methods and constructors need normal functions.

Arrow functions have no own this, arguments, super or new.target, and cannot be used as constructors. Use arrows for callbacks and small helpers; use methods or function when you need a dynamic this.

2.2Parameters, defaults and rest

Explain the behaviour

Defaults apply only for undefined, not for null or other values, and later parameters can reference earlier ones. Rest (...rest) collects leftover arguments into an array. Destructuring a parameter, with = {} as a default, gives named options that are safe to call with no argument.

Explain the behaviour

arguments is an array-like object available in normal functions (but not arrows). Spread (...) expands an iterable into a call or a literal, and Math.max(...nums) is the idiom for the max of an array. A function's .length counts parameters up to the first one with a default.

Tip

Prefer a single options object (fn({ retries: 3, timeout: 100 })) once a function takes more than two or three arguments. JavaScript has no named arguments, and destructured parameters are the idiom.

2.3Closures

A closure is a function bundled with the variables of the scope where it was defined. Those variables stay alive as long as the function does. Closures give you private state, factories, callbacks that remember context, and most functional patterns.

Coming from C++

Think of a lambda that captures everything by reference, except the garbage collector guarantees the captured variables never dangle.

Explain the behaviour

A function remembers the variables of the scope where it was defined, even after that scope has returned. Each call to counter() creates a brand-new count, so c1 and c2 are independent. That is private state in a language with no access modifiers.

Explain the behaviour

once wraps a function so it runs only the first time and caches the result — a closure over a done flag. memo caches by argument in a Map, so the expensive slowSquare only logs computing the first time it sees each input.

2.4How this works

this is decided at the call site, not where the function is written. Four rules, in priority order: (1) new f() makes a new object; (2) f.call(obj), f.apply(obj) or f.bind(obj) choose it explicitly; (3) obj.f() uses the object before the dot; (4) a plain f() call uses undefined in strict mode (and globalThis in sloppy mode). Arrow functions ignore all four and use the this of the enclosing scope.

Explain the behaviour

this is decided by how you call the function, in priority order: new makes a new object, call/apply/bind set it explicitly, a method call uses the object before the dot, and a plain call gets undefined in strict mode. Detaching a method (const f = a.whoAmI) turns it into a plain call.

Explain the behaviour

An arrow function has no own this; it uses the this of the surrounding scope. Inside timer.arrow, the arrow inherits timer as this, so it finds label. The regular method passes a normal function to map, whose this is undefined, so it prints undefined.

Explain the behaviour

Passing obj.method as a callback detaches it from obj, so a plain call later has the wrong this. The fixes: bind it in the constructor, or define it as a class-field arrow, which is bound per instance. The unbound onClick returns undefined while the other two work.

Gotcha

Passing obj.method as a callback (setTimeout(obj.method, 0), button.addEventListener('click', obj.method)) detaches it from obj. Bind it, wrap it in an arrow, or define it as a class-field arrow.

2.5Higher-order functions, currying and composition

Explain the behaviour

Currying turns a multi-argument function into a chain of single-argument calls. pipe threads a value left-to-right through a list of functions. Partial application pre-fills some arguments (partial(Math.pow, 2) is x → 2^x). All are just closures in disguise.

Explain the behaviour

Wrapper functions modify other functions' behaviour: logCalls logs every call and result, not inverts a predicate, and unary forces one argument — which fixes the parseInt/map bug by discarding the index that map passes as the radix.

2.6Recursion and the call stack

Explain the behaviour

Every call adds a frame to the call stack, which is finite, so deep recursion throws a RangeError. A trampoline rewrites recursion as a loop: each step returns a thunk (a zero-arg function) instead of calling itself, and the trampoline keeps running thunks until it gets a plain value — letting it sum to 100000 without overflowing.

The spec includes proper tail calls, but only Safari implements them. Never rely on tail-call optimisation in JavaScript: convert deep recursion to a loop, an explicit stack, or a trampoline like the one above.

2.7new.target, IIFEs and function objects

Explain the behaviour

new.target lets a constructor detect whether it was called with new and fix a missing new itself. An IIFE runs immediately, giving a private scope. Function.prototype is itself a function, a named function expression's name is visible only inside itself, and toString() returns the source.

03

Objects and prototypes

Object mechanics, destructuring, descriptors, prototype chains, classes, symbols, copying and JSON.

3.1Object literals and inspection

Coming from C++

Objects are hash maps with a prototype link, not structs with fixed layout. Properties can be added and removed at any time, though the engine optimises objects that keep a stable shape.

Explain the behaviour

Object literals support shorthand ({ id } means { id: id }), computed keys in brackets, method shorthand (greet() {}), and getters. A getter is read like a property but runs code each time it is accessed.

Explain the behaviour

Object.keys returns own enumerable string keys, with integer-like keys first in ascending order. in checks the whole prototype chain while hasOwn checks only the object itself. Object.fromEntries reverses entries, and Object.assign copies properties shallowly, later sources winning.

3.2Destructuring, spread and rest

Explain the behaviour

Destructuring pulls values out of arrays and objects into variables, with defaults for missing values and ... to collect the rest. It works in swaps, nested objects, and in for...of loop headers, making it the standard way to unpack data.

Explain the behaviour

Spread copies the top level only: { ...base } shares base.nested, so mutating the nested object shows through both. Later properties win in a merge. Spread also expands strings and arrays, and spreads into function calls like Math.min(...arr).

3.3Property descriptors, getters and freezing

Explain the behaviour

Every property has flags: writable, enumerable and configurable. A non-writable property silently ignores assignment in sloppy mode but throws in strict mode. Non-enumerable properties are hidden from Object.keys but still readable directly.

Explain the behaviour

Accessors turn property reads and writes into function calls, useful for computed or validated values. Object.freeze makes an object immutable but only shallowly — nested objects still change. Object.seal allows editing existing values but not adding or deleting keys.

3.4Prototypes and inheritance

Every object has an internal link to another object, its prototype. Property lookup walks that chain until it finds the key or reaches null. Classes are syntax on top of exactly this mechanism, so understanding prototypes explains instanceof, method sharing and super.

Coming from C++

The prototype chain is a runtime-mutable cousin of a vtable plus base-class lookup. Methods live once on the prototype and are found through the chain, not copied into each instance.

Explain the behaviour

Property lookup walks the prototype chain: dog.speak() finds speak on animal. Object.keys shows only own keys, while for...in also sees inherited enumerable ones. The chain ends at Object.prototype, whose prototype is null.

Explain the behaviour

A constructor sets up instance fields with this, and methods live on Constructor.prototype so every instance shares them. Inheritance means chaining prototypes with Object.create and calling the parent constructor with Person.call(this, ...). This is exactly what class does under the hood.

3.5Classes

Explain the behaviour

# fields are truly private: they cannot be read or listed from outside the class. Static members live on the class itself, getters expose computed values, and a static block runs once when the class is defined. Object.keys(acc) shows only public own fields, never private ones.

Explain the behaviour

extends wires the prototype chain; the subclass must call super() before touching this, and super.method() reaches the parent's version. instanceof walks the prototype chain. Extending Array produces real arrays, so map still returns a MyList.

Explain the behaviour

Classes are hoisted but stay in the temporal dead zone, so they cannot be used before their declaration. A class must be called with new — calling it directly throws. And typeof a class is 'function', because a class is just a constructor function with extra rules.

3.6Symbols and protocols

Explain the behaviour

Symbols are unique, non-string property keys that are skipped by normal enumeration but reachable with getOwnPropertySymbols. Symbol.for reuses a shared symbol by key. Well-known symbols like Symbol.toPrimitive and Symbol.toStringTag let objects customise how +, template strings and toString treat them.

Explain the behaviour

Symbol.hasInstance customises instanceof, Symbol.isConcatSpreadable controls whether an array-like spreads in concat, and Symbol.toPrimitive with a number hint lets +temp and temp1 > temp2 work numerically.

3.7Copying objects

Explain the behaviour

Spread copies one level, so shallow.inner and shallow.tags still point at the original's objects. structuredClone makes a fully independent copy, preserving dates and maps, but it throws on functions because they cannot be serialised.

Tip

structuredClone handles dates, maps, sets, typed arrays and circular references, but not functions, class instances' prototypes or DOM nodes. JSON.parse(JSON.stringify(x)) is a worse substitute: it drops undefined, functions and symbols, turns dates into strings and throws on cycles.

3.8JSON

Explain the behaviour

JSON.stringify drops undefined, functions and symbols, turns NaN/Infinity into null, and converts dates to strings. A replacer array acts as an allow-list of keys, and a toJSON method customises an object's representation.

Explain the behaviour

A reviver lets you turn specific values back into objects during JSON.parse — here dates. JSON requires double quotes, cannot represent circular structures, and rejects BigInt unless a replacer stringifies it first.

3.9Composition over inheritance

Explain the behaviour

A mixin is a function that takes a class and returns an extended class, letting you compose behaviours (Serializable, Eventful) without deep inheritance chains. class User extends Serializable(Eventful(Model)) stacks both onto Model.

Explain the behaviour

Instead of classes, plain factory functions can return an object assembled from behaviour mixins (canWalk, canSwim) spread together. State is captured in a closure, and the result is a simple object with the combined methods.

04

Collections and iteration

Arrays, Map and Set, iterators, generators, typed arrays.

4.1Arrays: creating, copying, mutating

Explain the behaviour

Array.from builds an array with a mapping function, and the ES2023 toSorted/toReversed/with return new arrays while sort mutates in place. slice copies a range; splice removes in place and returns what it removed.

Explain the behaviour

An empty slot is a hole, not undefined: forEach skips holes. length is writable, so shrinking it truncates and setting a far index stretches it. indexOf uses === (so it misses NaN) while includes uses SameValueZero (so it finds NaN). And typeof [] is 'object' — use Array.isArray.

4.2map, filter, reduce and friends

Explain the behaviour

map transforms, filter selects, reduce accumulates, flatMap maps then flattens one level, find/findLast/findIndex locate, and some/every test. flat(Infinity) flattens arbitrarily deep nesting, and Object.fromEntries turns mapped pairs into an object.

Explain the behaviour

reduce can build any aggregate: a group-by object, a frequency Map, or a max-by helper. ??= and ?? make the accumulation tidy, and reduceRight walks the array backwards.

Explain the behaviour

The default sort compares by string, so [10, 9, 1, 100] becomes [1, 10, 100, 9]; pass (a, b) => a - b for numbers. Sort is stable, so equal keys keep their order. Intl.Collator with numeric: true gives human-friendly ordering for things like item10 versus item2.

4.3Map, Set and the weak variants

Explain the behaviour

Map accepts any key type (objects, NaN) and preserves insertion order; Set stores unique values. ES2025 adds set algebra (union, intersection, difference, …) and Object.groupBy/Map.groupBy for bucketing.

Tip

Use Map when keys are not strings, when you add and delete often, or when insertion order and size matter. Use plain objects for fixed, known shapes and for JSON. Set gives O(1) membership tests where array.includes is O(n).

Explain the behaviour

Weak collections hold keys weakly, so an entry is garbage-collectable once nothing else references the key — ideal for attaching metadata without owning the object. Because entries can vanish at any time, they are not iterable and have no size.

4.4The iteration protocol

Explain the behaviour

Anything with a [Symbol.iterator] method returning a { next() } object is iterable, so it works with spread, for...of, destructuring and Array.from. Arrays, strings and maps all implement this same protocol.

Explain the behaviour

Iterator helpers (filter, map, take, drop, reduce) chain over any iterator lazily, so an infinite generator can be processed without materialising it. toArray collects the result at the end.

4.5Generators

Explain the behaviour

A generator (function*) yields values one at a time and pauses between them, so it can represent infinite sequences like ids or Fibonacci. yield* delegates to another generator — here to flatten a nested array.

Explain the behaviour

yield is two-way: the generator sends a value out, and the value passed to .next(x) comes back as the result of that yield. This turns a generator into a conversation. A return inside a generator ends iteration with { done: true, value }, and breaking a for...of triggers its finally.

4.6Typed arrays, ArrayBuffer and DataView

Coming from C++

This is the part of JavaScript closest to raw memory. An ArrayBuffer is a block of bytes; typed arrays and DataView are views onto it, like casting a void*. Endianness is explicit with DataView and platform-native for typed arrays.

Explain the behaviour

An ArrayBuffer is raw bytes; typed arrays and DataView are views over it. DataView reads/writes with explicit endianness, while typed arrays use the platform's. Uint8 values wrap modulo 256, Uint8ClampedArray clamps, and Float32Array is visibly less precise than a double.

Explain the behaviour

This shows a realistic binary layout: read a header with DataView, then decode a slice of the payload. subarray is a view sharing the same memory, while slice copies — a key distinction when you care about allocation.

05

Asynchronous JavaScript

The event loop, promises, async/await, cancellation and async iteration.

5.1The event loop

JavaScript runs your code on one thread. A single loop picks the next ready job and runs it to completion. There are two queues: the task queue (timers, I/O, UI events) and the microtask queue (promise reactions, queueMicrotask, await continuations). After every task, the engine drains the entire microtask queue before it takes the next task.

Coming from C++

It is the same shape as a single-threaded poll()/epoll loop: callbacks are your event handlers, they must return quickly, and anything that blocks stalls everything. A promise is a future with no threads behind it.

Explain the behaviour

Everything runs to completion in order: synchronous code first, then every queued microtask (promise reactions, queueMicrotask, code after await), and only then the next task from a timer. An async function body runs synchronously until its first await.

Explain the behaviour

After synchronous code, the engine drains the entire microtask queue — including microtasks scheduled by microtasks — before running the next task. That is why all three chained microtasks print before either setTimeout.

Gotcha

A long synchronous loop blocks the loop (the browser freezes, the server stops answering). A promise chain that keeps scheduling new microtasks can starve timers and rendering. Split heavy work into chunks with setTimeout, or move it to a Worker.

5.2Callbacks

Explain the behaviour

The Node convention passes (err, result) to a callback, so callers branch on err. But sequencing dependent async steps requires nesting each callback inside the previous one — the pyramid of doom that promises were invented to flatten.

5.3Promises

Explain the behaviour

A promise settles once, and each .then returns a new promise whose value is what the handler returns. Returning a promise flattens it; throwing rejects the chain, which .catch recovers and .finally always runs. After recovery the chain continues with the returned value.

Explain the behaviour

promisify wraps an error-first callback API in a promise. Promise.withResolvers gives you resolve/reject outside the executor, so code elsewhere can settle the promise — handy for wrapping event-style APIs.

Three rules explain most promise behaviour: a promise settles once; .then always returns a new promise whose value is whatever the handler returns (or throws); handlers always run asynchronously, as microtasks, even on an already-settled promise.

5.4async and await

Explain the behaviour

await pauses an async function until a promise settles and unwraps its value; a throw becomes a rejection you can catch. An async function always returns a promise, even when the body returns a plain value. Top-level await works in ES modules.

Explain the behaviour

awaiting one thing after another runs them in series (≈200 ms here); Promise.all starts them together and runs in parallel (≈100 ms). A for...of loop with await is sequential, while map plus Promise.all is parallel. forEach ignores the promises it creates, so it never waits.

Explain the behaviour

await turns a rejection into a throwable exception, so it can be caught by try/catch; without await, a returned rejected promise escapes the try. A throw inside a promise executor becomes a rejection, not a crash.

Gotcha

A rejected promise nobody handles raises unhandledrejection (and terminates Node by default). An exception thrown inside a setTimeout callback is not caught by an enclosing try/catch, because that code runs later on a different stack.

5.5Promise.all, allSettled, race, any

Explain the behaviour

all resolves to all values but rejects fast on the first error. allSettled never rejects and reports each outcome. race settles with the first to settle (success or failure). any resolves with the first success and rejects with an AggregateError only if all fail.

Explain the behaviour

Racing a promise against a timer that rejects gives a time limit: whoever settles first wins. This is the standard way to add a timeout to any promise, using Promise.race and a setTimeout rejection.

5.6Timers and scheduling

Explain the behaviour

setInterval calls a function repeatedly; clearInterval stops it. setTimeout runs once and can pass extra arguments to the callback. Always clear timers you no longer need so they do not keep running (and keep objects alive).

Explain the behaviour

setInterval can drift or pile up; a recursive setTimeout waits for each run to finish before scheduling the next, which self-corrects. Yielding to the loop with setTimeout(0) between chunks lets other work (and the UI) run, so nothing freezes.

Timer delays are minimums, not guarantees: the callback runs when the delay has elapsed and the loop is free. Browsers clamp nested timers to at least 4 ms and throttle background tabs heavily. Browsers also offer requestAnimationFrame (before the next paint) and requestIdleCallback; Node adds setImmediate and process.nextTick.

5.7Cancellation and timeouts

Explain the behaviour

An AbortController produces a signal you can pass to cancellable APIs; calling abort(reason) fires the abort event and rejects the promise with reason. AbortSignal.timeout self-aborts after a delay, and AbortSignal.any merges several signals.

fetch, streams, addEventListener and many Node APIs accept { signal }. Design your own async functions the same way: take an optional signal, pass it down, check signal.aborted between steps, and clean up in the abort listener.

5.8Async iteration

Explain the behaviour

for await...of awaits each item as it iterates, working with async generators and with arrays of promises. An async generator yields values after awaiting, so a consumer can process a stream with automatic backpressure. Array.fromAsync collects the result.

Node streams and fetch response bodies are async iterables, so for await (const chunk of stream) is the idiomatic way to consume them with automatic backpressure: the producer pauses while your loop body awaits.

5.9Concurrency patterns

Explain the behaviour

The pool runs at most limit tasks at once: it starts tasks, and when the running set reaches the limit it awaits a race to let one finish before starting the next. Results are written by index so input order is preserved, and peak confirms the limit was never exceeded.

Explain the behaviour

A mutex serialises access to shared state: each caller awaits lock() and releases in finally. Without it, both withdrawals would read 100 before either writes, losing an update — the classic read-modify-write race across an await.

06

Modern language features

Modules, errors, regex, tagged templates, Proxy, Intl and the newest built-ins.

6.1ES modules

Explain the behaviour

Modules export and import bindings; exports are live read-only links, not copies. import is static and hoisted, while dynamic import() returns a promise for lazy loading and code splitting.

Modules are singletons evaluated once; imports are live read-only bindings, not copies; they are always strict mode and have their own scope (top-level var does not leak to the global object). In a browser use <script type="module">. In Node use the .mjs extension or "type": "module" in package.json; CommonJS (require, module.exports) still exists, so you will meet both.

Gotcha

Circular imports work only if neither module uses the other's bindings during evaluation. If you hit a "Cannot access before initialization" error at startup, look for an import cycle.

6.2Errors and exceptions

Explain the behaviour

Custom errors subclass Error so instanceof still works, and the cause option links the original error. Different failures throw different error types (TypeError, ReferenceError, SyntaxError, RangeError, URIError), which is how you tell them apart.

Explain the behaviour

finally runs whether the try block returns, throws or succeeds — even running before a return completes. You can throw anything, but throwing Error objects is the convention. Re-throw errors you cannot handle, and use AggregateError to bundle many failures.

6.3Regular expressions

Explain the behaviour

Named groups ((?<year>…)) make matches readable, matchAll iterates all matches with positions, lookbehind ((?<=…)) and lookahead ((?!…)) assert context without consuming it, and the u flag plus \p{…} handle Unicode properly.

Explain the behaviour

A /g regex remembers lastIndex between calls, so test alternates true/true/false on the same input. Drop g (or reset lastIndex) when you just want to test. The sticky y flag matches only at exactly lastIndex.

Tip

Never build a regex from user input without escaping it, and be wary of nested quantifiers like (a+)+: they cause catastrophic backtracking that can freeze a server (ReDoS). Recent engines add RegExp.escape(); until then escape with s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&').

6.4Tagged templates

Explain the behaviour

A tag function receives the literal strings and the interpolated values separately, so it can transform them — escaping HTML for safety, or building a parameterised SQL query. s.raw gives the strings with escapes untouched.

6.5Proxy and Reflect

Explain the behaviour

A Proxy wraps a target and intercepts operations like get, set, has and delete. Reflect performs the default behaviour, so handlers can validate (age must be a number) or filter (hiding _ keys) before forwarding.

Explain the behaviour

Proxies can invent behaviour that does not exist on the target: a get trap that returns a default for missing keys, negative array indexes, or a tiny reactive object that runs a callback whenever a property changes.

6.6WeakRef and FinalizationRegistry

Explain the behaviour

WeakRef holds a reference that does not keep its target alive, and FinalizationRegistry runs a callback after collection. But collection timing is non-deterministic — a deref() can return the object even after big = null — so never build program logic on it.

6.7Dates and the Date object

Explain the behaviour

Date months are 0-based, and setMonth(1) on Jan 31 overflows into March. Date-only ISO strings are treated as UTC. An invalid date is a Date whose getTime() is NaN. Add days by adding milliseconds, not by mutating fields.

Explain the behaviour

Temporal replaces Date with separate types for a plain date, an exact instant, and a zoned moment. Arithmetic like add({ months: 1 }) and differences (until) handle calendar and timezone rules correctly.

Date stores milliseconds since the Unix epoch (always UTC) but its getters and toString use the viewer's local time zone. Store and transmit ISO 8601 UTC strings or epoch milliseconds, and convert to local time only for display.

6.8Intl: formatting for humans

Explain the behaviour

Intl formats values for humans and locales: numbers as currency/percent/units, dates in a timezone, relative times, plural and ordinal rules, and lists joined with the locale's conventions.

6.9A tour of recent additions

Explain the behaviour

A quick tour of recent additions: .at(-1), Object.hasOwn, non-mutating toSorted/toSpliced/findLastIndex, structuredClone, Object.groupBy, replaceAll, Promise.withResolvers, error cause, set union, and iterator helpers.

Explain the behaviour

These are arriving or stage-3 proposals: using for deterministic cleanup, Promise.try, RegExp.escape, decorators and more. Check tc39.es for current status before relying on them.

07

Under the hood

Scope chains, memory, garbage collection, engine optimisation and performance measurement.

7.1How an engine runs your code

Engines such as V8 (Chrome, Node), SpiderMonkey (Firefox) and JavaScriptCore (Safari) parse your source into an AST, compile it to bytecode, and start interpreting right away. Code that runs often ("hot" code) is recompiled by an optimising JIT compiler using assumptions gathered while it ran: this variable is always an integer, this object always has the same properties in the same order. If an assumption breaks, the engine deoptimises and falls back to slower code.

Two practical consequences. First, stable shapes: objects created with the same properties in the same order share a hidden class (a "shape"), which makes property access a fixed-offset load. Second, stable types: a function that always receives the same kinds of values stays monomorphic and fast; one fed a mix of numbers, strings and objects becomes megamorphic and slower.

Explain the behaviour

Engines optimise property access by assigning a hidden class (a shape) to objects with the same properties in the same order. Different property order, or adding properties later, creates new shapes and makes the same function polymorphic — slower. Initialise all fields in the constructor and avoid delete.

7.2Scope, execution contexts and the scope chain

Explain the behaviour

Scope is determined by where code is written, not where it is called: inner sees its own scope, then outer, then the global. An inner let shadows an outer one within its block. A closure reads the variables of its defining scope even when called elsewhere.

Every function call creates an execution context with a lexical environment: a table of its variables plus a link to the environment where the function was defined. Variable lookup walks that link chain. That chain is exactly what a closure keeps alive.

7.3Memory and garbage collection

JavaScript manages memory automatically with a tracing garbage collector: anything reachable from a root (the global object, the current call stack, live closures) is kept, everything else is eventually freed. A "leak" in JavaScript is therefore always unintended reachability: something you forgot still points at the object.

Coming from C++

There are no destructors and no RAII for memory, and collection time is not deterministic, so never rely on finalisation to release non-memory resources (file handles, sockets, locks). Use try/finally or the using declaration for those.

Explain the behaviour

An object is collected only when nothing reachable from a root points to it. A Map cache keeps every key alive forever; a WeakMap lets entries disappear with their keys. Event listeners and timers outlive their owner unless you remove them — always return a cleanup function.

Usual suspects in real leaks: unbounded caches and arrays, event listeners never removed, timers never cleared, closures capturing large objects they do not need, detached DOM nodes still referenced from JavaScript, and global variables created by accident. Find them with the heap snapshot and allocation timeline tools in the browser DevTools or node --inspect.

7.4Values, references and pass-by-sharing

Explain the behaviour

Mutation through a reference (o.changed = true) is visible to the caller; reassigning the parameter (o = {...}) only changes the local name. Objects compare by identity, so {} === {} is false while equal strings compare true by value.

JavaScript passes everything by value, but for objects the value is a reference. Hence "pass by sharing": the callee gets its own copy of the pointer, so it can mutate the shared object but cannot rebind the caller's variable.

7.5Measuring performance

Explain the behaviour

A benchmark warms up the JIT, runs several times and reports the median. The results are environment-specific and easily distorted, so treat them as rough hints — different techniques (preallocation, typed arrays, join versus +=) trade off in ways that depend on the engine.

Treat micro-benchmarks with suspicion: JIT warm-up, dead-code elimination and garbage-collection pauses distort them, and the numbers above change with your machine and browser. Profile real workloads (DevTools Performance tab, node --prof, console.time), fix algorithmic problems first (O(n²) loops, repeated parsing, needless re-renders), and only then micro-optimise.

Explain the behaviour

Replacing an O(n·m) includes search with an O(n+m) Set.has lookup makes the fast path win decisively. Fix algorithmic complexity before micro-optimising: the data structure matters far more than syntax-level tweaks.

7.6Debugging and the console

Explain the behaviour

console.table prints tabular data, group nests logs, assert only prints on failure, count tallies calls, dir shows object structure, and %s/%d format strings. Wrapping a variable in braces prints its name too.

Explain the behaviour

Beyond logging: debugger pauses under DevTools, console.trace prints the stack, console.time measures, breakpoints (including conditional and logpoints) avoid editing code, and source maps map bundled code back to sources.

08

Patterns and recipes

Reusable building blocks you will write again and again.

8.1Module pattern and singletons

Explain the behaviour

An IIFE captures private variables (count) in its closure and returns a frozen object exposing only the public API. The private state is unreachable from outside, giving real encapsulation without classes.

Explain the behaviour

A private static field caches the single instance, and ??= creates it on first use. Every call to get() returns the same object, so state set once is visible everywhere.

8.2Publish and subscribe

Explain the behaviour

An emitter maps event names to sets of listeners. on returns an unsubscribe function, once auto-removes after one call, and emit iterates a snapshot so listeners that unsubscribe during dispatch do not break the loop.

Explain the behaviour

EventTarget and CustomEvent are the platform's own pub/sub. dispatchEvent synchronously invokes listeners, and the { once: true } option auto-removes a listener after the first event — here the second ping finds no listener.

8.3Debounce and throttle

Explain the behaviour

debounce resets a timer on every call and fires only after events stop for ms, so a burst of keystrokes produces one search. throttle allows at most one call per ms, so scroll handlers fire at a steady maximum rate.

Debounce waits until events stop (search-as-you-type, window resize end). Throttle lets events through at a steady maximum rate (scroll, mousemove, progress updates).

8.4Retry with backoff

Explain the behaviour

retry loops until the function succeeds or attempts run out, waiting base × factor^attempt between tries and wrapping the final failure in an Error with a cause. The delay grows exponentially so retries do not hammer a struggling service.

Tip

In production add random jitter to the delay (delay * (0.5 + Math.random())) so many clients do not retry in lockstep, cap the maximum delay, and only retry errors that are actually transient (network failures, HTTP 429/503), never validation errors.

8.5An LRU cache

Explain the behaviour

A Map preserves insertion order, so deleting and re-inserting a key moves it to the most-recent end. The cache evicts the first (oldest) key when it exceeds capacity, giving least-recently-used semantics with no extra data structures.

8.6State machines and reducers

Explain the behaviour

Modelling the states and their legal transitions as a table makes invalid transitions impossible to express and the flow easy to read. The reducer pattern returns the next state from the current state and an event, instead of mutating flags scattered across the code.

Explain the behaviour

Each action returns a new state instead of mutating the old one, so the full history is preserved and nothing was mutated in place — which is why the original items: [] survives. This is the foundation of time-travel debugging and predictable state updates.

8.7Deep equality and handy utilities

Explain the behaviour

deepEqual compares by value recursively (using Object.is so NaN === NaN works), and small utilities like chunk, unique, zip, range, pick and omit are one-liners built on Array.from, Set and Object.fromEntries.

Browser and Node.js

The two main runtimes. These snippets are reference material: they need a real page or a Node install, so there is no Run button.

9.1The DOM

Explain the behaviour

Use querySelector for one element, querySelectorAll for a static list, textContent (not innerHTML) for untrusted text, and classList/dataset for class and data-attribute access. Event delegation attaches one listener on an ancestor and checks closest, and observers react to changes without polling.

Reading layout properties (offsetHeight, getBoundingClientRect()) right after writing styles forces a synchronous reflow. Batch all reads first, then all writes. Use DocumentFragment or replaceChildren to insert many nodes at once, and requestAnimationFrame for visual updates.

9.2fetch and the network

Explain the behaviour

fetch rejects only on network failure, not on 4xx/5xx — check res.ok. Send JSON with JSON.stringify and a content-type header, stream the body with for await, build query strings with URLSearchParams, and cancel with AbortController.

9.3Storage, workers and other web APIs

Explain the behaviour

A sampler: localStorage/sessionStorage for small string data, indexedDB for structured data, Worker for parallelism, BroadcastChannel for cross-tab messaging, requestAnimationFrame/requestIdleCallback for scheduling, and the URL API for parsing.

9.4Node.js essentials

Explain the behaviour

Node's fs/promises gives awaitable file IO, http builds servers whose request bodies are async-iterable, and pipeline wires streams together with correct backpressure and cleanup.

Node runs libuv's event loop with phases (timers, pending callbacks, poll for I/O, check for setImmediate, close callbacks). process.nextTick has its own queue, which in CommonJS code is drained before promise microtasks. File system, DNS lookups and crypto use a thread pool behind the scenes; your JavaScript still runs on one thread.

9.5Workers and CPU-bound work

Explain the behaviour

Worker threads run real parallel CPU work off the main loop. They do not share variables — they communicate by postMessage (structured clone) or by transferring ArrayBuffers, and SharedArrayBuffer + Atomics provides shared memory.

Workers do not share variables. They communicate with postMessage, which copies data with the structured clone algorithm, or transfers an ArrayBuffer without copying. SharedArrayBuffer plus Atomics gives true shared memory with atomic operations, in browsers (when cross-origin isolated) and in Node.

11.1Puzzle: numbers

Show the answer

false 0.30000000000000004 9007199254740992. Doubles cannot represent 0.1 or 0.2 exactly, and 9007199254740993 is above 2^53, so it rounds to the nearest representable value.

11.2Puzzle: coercion

Show the answer

Line 1: [object Object] true string. ![] is false, and [] == false converts both sides to 0. Line 2: [ 1, NaN, NaN ], because map passes the index as the radix. Line 3: NaN 0 0 5 NaN, since parseInt(null) parses the string "null".

11.3Puzzle: defaults

Show the answer

x 0 x x (the fourth value is an empty string). ?? only replaces null and undefined; || replaces every falsy value.

11.4Puzzle: hoisting

Show the answer

undefined, then function undefined. Inside f the local var a is hoisted and shadows the outer one, but its assignment has not run yet. The function declaration g is fully hoisted; h is only declared, not yet assigned.

11.5Puzzle: getters

Show the answer

2 11. Destructuring calls the getter once and stores the resulting value; reading o.b later runs the getter again with the new a.

11.6Puzzle: this

Show the answer

obj undefined undefined obj. The comma expression (0, obj.regular) evaluates to the bare function and loses the reference to obj; plain parentheses (obj.regular) keep it.

11.7Puzzle: object keys

Show the answer

[ '1', '[object Object]' ] 2. Property keys are strings (or symbols), so 1 and '1' collide and every plain object becomes the same string [object Object]. A Map would keep them apart.

11.8Puzzle: the event loop

Show the answer

A D F C E B. Synchronous code first (A, then D from inside the async function, then F). Then microtasks in order they were queued (C, E). The timer is a task and goes last.

11.9Puzzle: microtask interleaving

Show the answer

6 1 3 5 2 4. The first round of reactions (1, 3, 5) is already queued when the synchronous code finishes. Each .then(…) that follows is queued only after its predecessor ran, so 2 and 4 come after 5.

11.10Puzzle: closures in loops

Show the answer

var 3 three times, then let 0, let 1, let 2. A var loop shares one binding that is already 3 when the timers fire; a let loop creates a fresh binding per iteration.
